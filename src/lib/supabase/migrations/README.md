# Database migrations

## How the schema is defined

| What | Where |
|---|---|
| **Rune 2.0 schema** (canonical; builds a new database in one step) | `../schema.sql` — generated by `tools/sync-harness/build-schema.mjs`; do not edit by hand |
| **Rune 1.x baseline:** the `public` schema production ran on 2026-09-24 | `../baseline/production-2026-09-24.sql` — generated from the catalog below; do not edit by hand |
| The production catalog the baseline was generated from | `../catalog/production-2026-09-24.json` |
| Changes since the baseline | `013_…sql` onward, applied in order |
| History (already inside the baseline) | `001_…sql` to `012_…sql`. **Never re-run.** |

`schema.sql` is the baseline plus every migration from `013` onward, applied
in PGlite, captured with `tools/db-audit/catalog.sql`, and written out by the
same generator as the baseline. It records the migrations it contains in
`public.schema_migrations`. A new Rune 2.0 database is built from
`schema.sql` alone; an existing database receives the numbered migrations it
has not recorded, in order.

Production (Rune 1.x, real writers) is still the baseline plus `013`/`014`.
Migration `015` is **not** for production: it refuses to run on any database
holding manuscript data. Moving production to the Rune 2.0 schema is a
separate, future data migration.

Migrations 001–012 must not be replayed. They assume tables no migration
creates, and several aren't idempotent. Re-running `007` silently regresses
signup (`handle_new_user` stops creating pricing entitlements).

Every database records what it has received in `public.schema_migrations`
(created by `013`).

| `013` | every database | the `schema_migrations` ledger |
| `014` | every database | read-only assertions that the database is the 2026-09-24 baseline |
| `015` | the **empty** Rune 2.0 database only | Rune 2.0 manuscript foundation: `manuscripts`, `chapters.manuscript_id`, `scenes` (replaces `pages`), `writing_sessions.scene_id`, `save_scene_checked` / `insert_scene_checked`, no canonical behavior |

| `023` | the Rune 2.0 database (after `022`) | Workspace Pages: `workspace_documents` (per-Project freeform documents; never `pages`, never manuscript prose); `version` bumped by the database on content change only; RLS select/insert/update by Project owner; no client DELETE until Trash; a Page never changes Project; nothing existing changes |
| `024` | the Rune 2.0 database (after `023`) | Workspace tree: `workspace_folders` (organisational only) and `workspace_nodes` (one canonical node per Page/Folder, only a Folder has children, no cycles, siblings 1..n); RPCs `create_workspace_document`, `create_workspace_folder`, `move_workspace_node`, `delete_workspace_folder` (empty only); insert trigger places every new Page/Folder, including direct inserts from pre-024 clients; existing Pages backfilled to the top level in creation order. **Apply before** the app deploy that uses it (the new app creates Pages through `create_workspace_document`) |
| `025` | the Rune 2.0 database (after `024`) | Workspace Collections: `workspace_collections` (one canonical node each; `workspace_nodes` gains `collection_id` / target type `collection`; never a tree parent) and `workspace_collection_entries` (belong to one Collection for life, content-versioned like Pages, RLS by Project owner, no client DELETE); RPCs `create_workspace_collection`, `delete_workspace_collection` (empty only). No existing row changes. **Apply before** the app deploy that uses it (the new loader reads `workspace_collections`) |
| `026` | the Rune 2.0 database (after `025`) | Collection Properties: `workspace_collection_properties` (typed definitions — text, number, select, multi_select, status, date, checkbox — with Collection-owned options, order and list visibility) and `workspace_entry_values` (one checked value per Entry and property; composite FKs make another Collection's property impossible). Clients only read both; writes via `create/update/move/delete_workspace_collection_property` and `set_workspace_entry_value`. Deleting a property requires the confirmed value count. Adds `unique (id, collection_id)` to `workspace_collection_entries`; no existing row changes. **Apply before** the app deploy that uses it (without it the app shows no properties) |
| `027` | the Rune 2.0 database (after `026`) | Collection Views: `workspace_collection_views` (saved List / Table / Board configuration per Collection — shown properties and their order, sort, small AND filters, Board grouping by a select/status property). A new Collection gets a List View; every existing Collection is backfilled with one showing its `shown_in_list` properties. Clients only read; writes via `create/update/move/delete_workspace_collection_view` (the last View can't be deleted). | `028` | the Rune 2.0 database (after `027`) | References: `object_references` (canonical forward references between Entries, Pages and Scenes of one Project — a generic link, or one value of a Relationship property; typed FK columns, same-Project enforced, a permanently deleted end removes the row but never the other end). Backlinks are derived by target, never stored. `workspace_collection_properties` gains the `relationship` type and `relation_target` / `relation_collection_id` / `relation_many`; `workspace_collection_entries` gains unique `(id, project_id)`. `prune_workspace_view_config` (a Relationship never sorts) and `delete_workspace_collection_property` (counts a Relationship's values) are replaced. Clients only read; writes via `create/update_workspace_relationship_property`, `set_workspace_entry_relationship`, `add/remove_object_reference`. | `029` | the Rune 2.0 database (after `028`) | Project Search: `search_project_content(project, query, limit)` finds text inside the Project's Scenes (placed and Unplaced), Workspace Pages and Collection Entries, returning `[{ type, id, snippet }]`. SECURITY INVOKER (the caller's RLS) and owner-only, STABLE, read-only; anon has no execute. Over `rich_text_plain(jsonb)`, the readable text of a TipTap document (text nodes only), derived per request and never stored. No table, column, index, policy, row or manuscript function changes. | `035` | the Rune 2.0 database (after `034`) | Inline references in Workspace rich text: `object_references.origin` (`'link'` — every existing row — or `'inline'`) and a Chapter target (`target_type 'chapter'`, `target_chapter_id` FK ON DELETE CASCADE). | `036` | the Rune 2.0 database (after `035`) | Scene History and named Manuscript Milestones: new tables `scene_revisions`, `manuscript_milestones`, `manuscript_milestone_scenes` (RLS: owner reads; no client writes). No existing table, column, function, policy, RPC signature or row changes. **Apply before** the app deploy that offers History and Milestones (without it they are refused and nothing is written); applying it earlier is safe — the previous app's saves simply start leaving checkpoints |

## Rules for a new migration

1. Next number, one concern per file: `016_short_description.sql`.
2. Start with the guard, and end by recording the migration (template below). A
   migration that is already recorded must refuse to run.
3. Compatibility contracts stay intact unless an explicit, staged task
   changes them. On production (Rune 1.x) that covers the `pages` table and
   Page IDs, the save-path RPC signatures, argument names, return shapes and
   status values (no new overloads, no new statuses), and the columns stale
   clients read. On Rune 2.0 the same applies to `scenes`,
   `save_scene_checked` and `insert_scene_checked` once a deployed client
   depends on them.
4. Say which databases the migration is for, and guard it (015 refuses
   non-empty databases). Add a regression test in `tools/sync-harness/tests/`
   that applies it and asserts its effect, including its catalog diff
   (`diffCatalogs`), as `schema-equivalence.test.mjs` does for 013/014 and
   `rune2-schema.test.mjs` does for 015.
5. Regenerate `schema.sql`: `npm --prefix tools/sync-harness run schema`.
   `npm test` fails while it is stale.
6. Rehearse it on staging, then apply it to production, following
   `tools/db-audit/STAGING.md`. That covers the manual backup, the backup
   check, the staging run, an exact expected diff, and rollback.
7. After production, re-capture the catalog, commit the new snapshot,
   regenerate the baseline (`node tools/db-audit/generate-schema.mjs …`), and
   update the equivalence test's snapshot path.

## Template

```sql
-- ── Migration 0NN: <what and why> ───────────────────────────────────────────
-- <Rationale. What it changes. What it deliberately does not change.>
-- Rollback: <exact statements>
-- Apply as ONE script, following tools/db-audit/STAGING.md.

do $$
begin
  if to_regclass('public.schema_migrations') is null then
    raise exception 'Migration 0NN requires migration 013 (schema_migrations). Nothing was changed.';
  end if;
  if exists (select 1 from public.schema_migrations where version = '0NN') then
    raise exception 'Migration 0NN has already been applied. Nothing was changed.';
  end if;
end
$$;

-- … changes …

insert into public.schema_migrations (version, name, applied_at, note)
values ('0NN', '0NN_short_description.sql', now(), '<one line>');
```

The Supabase SQL editor runs a pasted multi-statement script as one
transaction, so any error rolls back everything. With psql, use `-1`.
